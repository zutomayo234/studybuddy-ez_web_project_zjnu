# AI 使用公约与记录

> 对应《团队规范项目实训》要求：建立"团队 AI 使用公约"，明确哪些环节可用 AI、如何标注 AI 产出、如何做人工复核；
> 每份实验报告末尾需附"AI 工具使用记录"。

## 一、AI 使用公约（红线与允许范围）

### 1.1 允许使用 AI 的环节

| 环节 | 允许程度 | 说明 |
| --- | --- | --- |
| 资料检索与概念解释 | ✅ 鼓励 | 快速理解 Spring Security、RAG 等概念 |
| 生成脚手架 / 样板代码 | ✅ 允许 | Entity、DTO、Mapper XML 等重复性代码 |
| 生成单元测试 | ✅ 允许 | 但需人工补充边界用例 |
| 代码评审辅助 | ⚠️ 参考 | 仅作为初步意见，人工评审为最终责任方 |
| 排查编译/报错 | ✅ 允许 | 由人工确认根因后再修改 |
| 文档润色 | ✅ 允许 | 技术结论必须人工核对 |

### 1.2 禁止事项

1. **禁止直接提交未理解的 AI 生成代码**——教师会随机抽测代码讲解；
2. **禁止把整模块外包给 AI 后不复核**；
3. **禁止将敏感信息送入公网模型**：数据库密码、API Key、真实用户手机号/身份证一律不得上传；
4. **禁止让 AI 决定架构与安全方案**——关键决策必须人工拍板。

### 1.3 标注规范

- AI 参与生成的代码，在关键行或方法头加注释 `// AI-assisted`，并在 PR 描述中登记；
- 关键逻辑（密码加密、鉴权、注入防护）必须有人工复核痕迹（补充注释说明"为什么这么做"）。

## 三、AI 出错与幻觉案例记录（实验五要求）

| 案例 | 现象 | 根因 | 应对措施 |
| --- | --- | --- | --- |
| 案例1：RAG 误召回 | 提问"今天天气怎么样适合钓鱼吗"，朴素关键词检索却召回了课程知识库片段 | 中文按单字建索引，"适合"等常见二元组与知识库偶然重合 | ① 建立中文停用词表；② 只以"实义词（长度≥2 且非停用词）"判定相关性；③ 要求至少命中 2 个实义词（问题只有一个实义词时放宽为 1）；④ 补充单元测试锁定该行为 |
| 案例2：依赖版本幻觉 | AI 建议的 jjwt 版本号与 API 写法不匹配（旧版 `Jwts.parser().setSigningKey()` 已废弃） | 模型训练数据滞后于库的版本演进 | 以 Maven 实际下载的 0.12.6 为准，改用 `Jwts.parser().verifyWith(key)`；编译报错驱动修正 |
| 案例3：密码哈希构想 | 想让 AI 直接给出一个可写进 SQL 的 BCrypt 密文 | BCrypt 每次加密带随机盐，密文不可复用；写死密文既不通用也可能失效 | 改为应用启动时用当前 `PasswordEncoder` 生成默认账号密码（`DataInitializer`），SQL 中不出现任何密码 |
| 案例4：跨域配置误解 | AI 建议用 `allowedOrigins("*")` 并开启 `allowCredentials(true)` | 该组合会被浏览器直接拒绝 | 改为配置精确白名单（`http://localhost:5173`），并在前端开发阶段叠加 Vite 代理 |

## 四、反思

1. **AI 是生产力工具，不是责任主体**：本项目 5 个实验中，AI 显著加快了脚手架与样板代码的产出，
   但在"检索相关性""密码存储""跨域安全"这三处都出现过需要人工纠正的问题，其中 RAG 的缺陷是**由单元测试暴露**的
   ——这恰好说明"AI 生成 + 人工测试验证"才是可靠组合。
2. **提示词质量直接决定产出质量**：把"角色 + 约束 + 上下文 + 任务 + 输出格式"写清楚后，
   同一需求的一次通过率明显提高（见 `ai-demo/prompt_engineering_demo.py`）。
3. **边界意识**：密钥与密码一律走环境变量，是全程坚守的底线；
   不把敏感数据送进公网模型，是使用 AI 时的硬约束。
