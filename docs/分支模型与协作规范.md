# 分支模型与协作规范（实验三）

> 对应《团队规范项目实训》"团队规范"要求：分支模型、PR 评审、代码规范、例会制度。

## 一、分支模型

采用简化的 Git Flow：

```
main        ●────────────────●────────────●─────────►  仅存放可发布版本（受保护）
             ↑                ↑            ↑
             │  Merge PR      │            │
develop     ●───●───●────●────●───●────●───●─────────►  集成分支，随时可构建
                 ↑    ↑        ↑
                 │    │        │
feature/*   ●────●    ●────────●                       功能分支，一事一分支
hotfix/*             （从 main 拉出，修复后同时合回 main 与 develop）
```

| 分支 | 命名 | 来源 | 合并去向 | 说明 |
| --- | --- | --- | --- | --- |
| main | `main` | — | — | 生产分支，**受保护**，禁止直接 push |
| develop | `develop` | main | main | 集成分支，日常开发基线 |
| feature | `feature/exp1-user-crud` | develop | develop | 单个实验/功能 |
| hotfix | `hotfix/ci-fix` | main | main + develop | 紧急修复 |

本课程五个实验对应五个功能分支，便于追溯：

```bash
git checkout -b feature/exp1-springboot-crud develop
# ...开发...
git add . && git commit -m "feat(exp1): 完成后端工程骨架与用户表 CRUD"
git push -u origin feature/exp1-springboot-crud
# 在 GitHub 上发起 Pull Request → 至少 1 人评审 → 合并到 develop
```

## 二、常用命令速查

```bash
# 1. 初始化
git init
git add .
git commit -m "chore: 初始化 StudyBuddy 项目结构"

# 2. 关联远程并推送
git remote add origin git@github.com:<your-name>/studybuddy.git
git branch -M main
git push -u origin main

# 3. 创建并切换功能分支
git checkout -b feature/exp1-springboot-crud

# 4. 查看状态/差异
git status
git diff
git log --oneline --graph --all

# 5. 提交（遵循 Conventional Commits）
git commit -m "feat(exp1): 新增用户分页查询接口"

# 6. 把 develop 的最新改动同步到当前分支（减少冲突）
git fetch origin
git rebase origin/develop      # 或 git merge origin/develop

# 7. 合并到 develop（本地演练）
git checkout develop
git merge --no-ff feature/exp1-springboot-crud

# 8. 解决冲突后继续
git add <冲突文件>
git rebase --continue          # 或 git commit
```

## 三、提交信息规范（Conventional Commits）

格式：`<type>(<scope>): <subject>`

| type | 含义 | 示例 |
| --- | --- | --- |
| feat | 新功能 | `feat(exp4): 新增 JWT 登录接口` |
| fix | 缺陷修复 | `fix(rag): 修正无关问题误召回` |
| docs | 文档 | `docs: 补充接口文档` |
| refactor | 重构 | `refactor(service): 抽取 VO 转换方法` |
| test | 测试 | `test(rag): 补充检索单元测试` |
| chore | 构建/工具 | `chore(ci): 添加前端构建任务` |

**为什么要规范提交信息**：便于生成变更日志、快速定位问题引入点、让 Code Review 更有上下文。

## 四、Pull Request 与 Code Review

PR 模板见 `.github/pull_request_template.md`。评审检查清单：

- [ ] 功能是否与 PR 描述一致，有无夹带无关改动
- [ ] 命名是否清晰（变量、方法、类）
- [ ] 是否有重复代码可以抽取
- [ ] 异常是否被处理，是否有吞异常的情况
- [ ] **安全**：有无密钥/密码硬编码、有无 SQL 拼接、有无越权风险
- [ ] 是否补充了测试与文档
- [ ] 是否按规范标注了 AI 参与的代码（`// AI-assisted`）

**责任界定**：AI 可以辅助生成评审意见（PR 摘要、潜在 bug 提示），但**人工评审是最终责任方**，
AI 的意见只能作为参考，不能替代人的判断。

## 五、冲突解决演练（实验三步骤要点）

模拟场景：两位成员同时修改了 `README.md` 的同一行。

```bash
# 成员 A 在 feature/a 分支修改并提交
# 成员 B 在 develop 上修改同一行并提交
# A 合并 develop 时产生冲突

git checkout feature/a
git merge develop
# Auto-merging README.md
# CONFLICT (content): Merge conflict in README.md

# 打开 README.md，会看到冲突标记：
# <<<<<<< HEAD
#   成员 A 的版本
# =======
#   成员 B 的版本
# >>>>>>> develop

# 人工协商后保留正确内容，删除标记，然后：
git add README.md
git commit -m "merge: 解决 README 冲突，保留成员 A 的措辞"
```

**关键点**：冲突标记必须人工确认，不能盲目保留一方；跨分支频繁同步（小步提交）能显著减少冲突规模。

## 六、例会制度

- 每 Sprint 站会 ≤ 15 分钟，回答三个问题：昨天做了什么 / 今天做什么 / 有什么阻塞；
- 评审会展示可运行版本，记录遗留问题；
- 例会记录归档到 `docs/meeting/`（本课程为个人实训，此处作为团队项目的规范约定）。
